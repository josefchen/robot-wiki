Scene representation is a robot's memory of its surroundings, from point clouds and occupancy grids to distance fields and neural fields, in a form planners can query <Cite id="cadena-2016" /><Cite id="neural-fields-survey-2024" />. The format decides which questions the robot can answer, and how fast.

<Image id="ouster-lidar-point-cloud-sf" />

## Each format answers different questions

<SceneRepresentationLadder className="my-6" />

A home robot fetching a mug asks whether the floor is free, which way the mug's surface faces, and what the room looks like from a spot it never visited. No single format answers all three well. Cadena and colleagues judge formats by storage, construction cost and usefulness for the task <Cite id="cadena-2016" />.

### Occupancy grids know what nobody has seen

A <Term id="point-cloud">point cloud</Term> is an unordered set of 3D points <Cite id="pointnet-2017" />, and it cannot tell empty space from unobserved space. An <Term id="occupancy-grid">occupancy grid</Term> can: Moravec and Elfes marked each sonar beam's interior probably empty and its far end possibly occupied, and overlapping readings refined each cell <Cite id="moravec-elfes-1985" />. OctoMap carries the three states into 3D in compressed octrees <Cite id="octomap-2013" />.

<ExplainerFigure id="mug" />

### Signed-distance fields tell a planner how far to push

A <Term id="signed-distance-field">signed distance function</Term> stores the distance to the nearest surface, signed by side, which is what a planner pushing a trajectory off obstacles needs. Curless and Levoy fuse depth images into one weighted field and take the surface at its zero crossing <Cite id="curless-levoy-1996" />. KinectFusion did it live, fusing 640×480 Kinect depth at 30 Hz on a commodity GPU <Cite id="kinectfusion-2011" />.

<Image id="kinect-xbox-360-sensor" />

| Method | Gain |
| --- | --- |
| Voxel hashing | Stores data only near observed surfaces <Cite id="voxel-hashing-2013" /> |
| Voxblox | Builds TSDFs faster than OctoMap builds maps and derives Euclidean distance fields from them incrementally <Cite id="voxblox-2016" /> |
| nvblox | On GPU, up to 177x faster reconstruction and 31x faster distance fields <Cite id="nvblox-2023" /> |

### Neural fields render views nobody captured

A mesh adds faces with normals but leaves holes where nothing was seen, and filling them invents geometry <Cite id="curless-levoy-1996" />. NeRF fits a <Term id="neural-radiance-field">neural radiance field</Term> to posed photographs, and differentiable rendering lets image error drive the fit <Cite id="nerf-2020" />. <Term id="gaussian-splatting">3D Gaussian splatting</Term> fits small semi-transparent blobs instead and renders 1080p in real time on an A6000 <Cite id="3dgs-2023" />.

| Method | Adds |
| --- | --- |
| NeRF++ | Unbounded 360-degree scenes <Cite id="nerfpp-2020" /> |
| Instant NGP | Hash encoding: a large 360-degree scene at 10 frames per second on one RTX 3090 <Cite id="instant-ngp-2022" /> |
| gsplat | Open splat training with up to 4 times less memory <Cite id="gsplat-2024" /> |

### Networks now predict geometry straight from images

Feed-forward networks predict geometry in one pass, without per-scene optimization or, often, known cameras:

| Model | Input | Output |
| --- | --- | --- |
| DUSt3R (2024) | Two images, no intrinsics or poses | Dense 3D points in the first camera's frame, at unknown scale <Cite id="dust3r-2024" /> |
| MASt3R (2024) | Two images | Adds descriptors for fast reciprocal matching <Cite id="mast3r-2024" /> |
| CUT3R (2025) | Image sequence, with recurrent state | Metric points in a shared frame, including unseen views <Cite id="cut3r-2025" /> |
| VGGT (2025) | One to hundreds of views | Cameras, points, depth and tracks in under one second <Cite id="vggt-2025" /> |
| MapAnything (2025) | Images plus optional intrinsics, poses or depth | Metric geometry <Cite id="mapanything-2025" /> |
| Pi3 (2025) | Any views, treated equally | Output independent of which view comes first <Cite id="pi3-2025" /> |
| Depth Anything 3 (2025) | Any view collection, with or without poses | Depth and rays <Cite id="depth-anything-3-2025" /> |

## A radiance field is geometry for rendering

A splat is a learned renderer: appearance is learned, physics is not, as the [world-models taxonomy](/world-models/taxonomy) puts it. In the original 3DGS a blob's opacity is a blending weight, with no free, occupied or unknown label <Cite id="3dgs-2023" />. Also: SuGaR's meshes from surface-aligned Gaussians <Cite id="sugar-2023" />, 2D Gaussian Splatting's flat disks <Cite id="2dgs-2024" />.

Simulators therefore pair splats for appearance with separate physics.

| System | Physics from | Result |
| --- | --- | --- |
| SplatSim | PyBullet | Zero-shot real transfer of diffusion policies on four rigid-body tasks <Cite id="splatsim-2024" /> |
| RoboGSim | Isaac Sim, for inverse kinematics and contact | Closed-loop policy evaluation on splat-rendered images <Cite id="robogsim-2024" /> |
| Isaac Sim | Its own engine | Loads splats as OpenUSD particle fields beside polygons <Cite id="isaac-sim-nurec-docs-2026" /> |

Other fields serve a planner directly.

| Field | Use |
| --- | --- |
| Dex-NeRF | Depth for transparent objects, where a RealSense failed on most of those tested <Cite id="dex-nerf-2021" /> |
| F3RM | Foundation-model features in 3D, so language and a few demonstrations guide grasping <Cite id="f3rm-2023" /> |
| ParticleSplat (2026) | Latent particles that decode to Gaussians; masks emerge without labels, and moving a particle moves its object <Cite id="particlesplat-2026" /> |

## SLAM builds the map and the position together

A robot in an unknown kitchen needs a map to localize and a position to map, so simultaneous localization and mapping (SLAM) builds both. A sensor-specific front end turns measurements into constraints on poses and landmarks; a back end solves for the most likely map and trajectory <Cite id="cadena-2016" />. Square Root SAM solves it as one sparse least-squares problem <Cite id="dellaert-kaess-2006" />, and iSAM2 updates it incrementally <Cite id="kaess-2012" />.

<Image id="velodyne-hdl64-lidar-2009" />

Front ends track features or work on raw brightness. [State estimation](/classical/state-estimation) covers the back end.

| Front end | How it works |
| --- | --- |
| ORB-SLAM (2015) | Tracks ORB features, refines them by local bundle adjustment, proposes loops with DBoW2 <Cite id="orb-slam-2015" /> |
| DBoW2 | A vocabulary tree of binary features; rejects look-alikes that fail geometric checks <Cite id="dbow2-2012" /> |
| ORB-SLAM3 | Adds stereo, RGB-D and visual-inertial modes; low texture is its main failure <Cite id="orb-slam3-2021" /> |
| Direct Sparse Odometry | Minimizes brightness error, so it uses any gradient, even on near-blank walls <Cite id="dso-2018" /> |
| Cartographer | Matches 2D LiDAR scans to submaps <Cite id="cartographer-2016" /> |

Learned SLAM keeps the classical skeleton and swaps in learned parts:

| System | What is learned or new | Note |
| --- | --- | --- |
| DROID-SLAM (2021) | Iterates pose and per-pixel depth through a dense bundle-adjustment layer | <Cite id="droid-slam-2021" /> |
| iMAP (2021) | A scene-specific network trained from scratch on a handheld RGB-D stream | Tracks at 10 Hz, maps at 2 Hz <Cite id="imap-2021" /> |
| NICE-SLAM (2022) | Hierarchical feature grids with pretrained decoders | Multi-room apartment, no loop closure <Cite id="nice-slam-2022" /> |
| SplaTAM (2023) | RGB-D mapping with 3D Gaussians | Silhouette mask marks mapped areas <Cite id="splatam-2023" /> |
| Gaussian Splatting SLAM (2023) | Camera optimized directly against the Gaussians | Monocular <Cite id="monogs-2023" /> |
| MASt3R-SLAM (2024) | Learned two-view reconstruction prior | Tracking, fusion, loop closure, global optimization <Cite id="mast3r-slam-2024" /> |
| SLAM3R (2024) | Points predicted for overlapping video windows | No explicit camera solving <Cite id="slam3r-2024" /> |
| VGGT-SLAM (2025) | Submaps aligned with projective transforms | Uncalibrated monocular <Cite id="vggt-slam-2025" /> |
| VGGT-SLAM 2.0 (2026) | Redesigned factor graph | About 23% less pose error on TUM; online on a ground robot's Jetson Thor <Cite id="vggt-slam-2-2026" /> |
| AMB3R-SLAM (2026) | Light tracking front end, hierarchical back end | Consistency over long trajectories <Cite id="amb3r-slam-2026" /> |

### A false loop closure does more harm than a missed one

Every odometry method drifts, and returning to a mapped place pulls the whole trajectory back into line <Cite id="cadena-2016" />. ORB-SLAM checks a <Term id="loop-closure">loop closure</Term> geometrically, then spreads the correction with pose-graph optimization <Cite id="orb-slam-2015" />.

<LoopClosure className="my-6" />

<Term id="place-recognition">Place recognition</Term> fails both ways: one place changes with light and season, and different places look alike <Cite id="lowry-2016-place-recognition" />. A false match can corrupt the back end, while a missed one only loses information <Cite id="cadena-2016" />. Graduated non-convexity sharpens a robust objective step by step and needed no initial guess in the problems tested <Cite id="gnc-2019" />.

Also: AnyLoc's place descriptors from frozen self-supervised features <Cite id="anyloc-2023" />.

## Mobile robots navigate on costmaps

Mobile robots mostly plan on a <Term id="costmap">costmap</Term>: occupancy inflated by the robot's footprint, so the robot can be planned as a point. Layered costmaps stack the static map, sensed obstacles and inflation into one 2D grid <Cite id="layered-costmaps-2014" />. Navigation2 uses one, with a global planner for the route and a controller for local commands <Cite id="nav2-2020" />.

Its `track_unknown_space` option defaults to false, which treats unknown space as free <Cite id="nav2-costmap-2d-2026" />.

## A representation is a service contract

Each consumer asks the map a different question. Localization needs stable landmarks and rendering needs appearance <Cite id="cadena-2016" />, collision checking needs occupied volume with a conservative update rule <Cite id="octomap-2013" />, and [perception](/classical/perception) locates objects in the current frame <Cite id="conceptgraphs-2023" />.

Scene graphs stack several answers in one structure.

| Scene graph | Adds |
| --- | --- |
| Hydra | A real-time distance field, then places, then rooms <Cite id="hydra-2022" /> |
| MoMa-SG (2026) | A drawer's axis, and which objects sit in which containers <Cite id="moma-sg-2026" /> |
| Maggio, Hauser, Carlone and colleagues (2026) | A full mobile-manipulation stack from one uncalibrated camera, with change detection <Cite id="found-it-mobile-manipulation-2026" /> |
| ConceptFusion | Foundation-model features that text, images, audio or geometry can query <Cite id="conceptfusion-2023" /> |

Some maps are now text.

| Text map | Result |
| --- | --- |
| SceneLM (2026) | One VLM edits an object list after each image; competitive on language-grounded retrieval with a map 6 to 12 times smaller, online on a quadruped <Cite id="scenelm-2026" /> |
| Ledger (2026) | Persistent object memory from egocentric video; lifted GPT-5.4 on HD-EPIC from 29.7% to 42.6%, 0.99 m median error on Ego4D <Cite id="ledger-2026" /> |

A deployed map states its frame, timestamp, resolution, unknown-state convention, update rate and expiry. In MoveIt 2, attached or removed objects must reach the planning scene before the arm moves <Cite id="moveit-planning-scene-2026" />. A world model must also say how actions change the scene, as the [simulator comparison](/world-models/world-models-vs-simulators) explains.
